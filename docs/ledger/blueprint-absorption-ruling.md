## 二、逐条裁决

### 分歧 1：对话方式 —— 选 C（结合·分级）

**决策**：默认维持安静脑暴 + 旁观编译；新增「探索模式」作为可选通道。

- **用户原话（七行勾选）**：「同意如上」
- **用户原话（探索模式触发器）**：「同意」——「帮我想想」手动触发 + 覆盖度仅提示
- **触发器（用户拍板口径）**：以用户主动触发为主——画布/右栏提供「帮我想想」入口；覆盖度评分仅作提示卡（「还有 N 类常见场景没聊到」），不自动切换模式、不连珠炮追问。
- **边界**：探索模式下 AI 可主动提问，但①一次一问；②所有产出实体标 `ai_inferred`；③默认值必须可一键拒绝；④提问内容进 provenance，可审计。
- **否决**：B（蓝图式全程主动追问）——与防诱导、原话主权原则冲突，「问着问着变成 AI 的方案」风险不可控；纯 A——「有痛点没词汇」用户的认知空白无机制兜底。
- **影响**：预登记——落地时评估是「增补例外通道」还是「SUPERSEDE ADR-0014 部分条款」。若探索提问仅经 `partner_hint`/画布卡表达、右栏仍无系统 prompt，倾向前者；若要求 AI 直接开口追问，则必须 SUPERSEDE。本裁决不立即改 ADR。

### 分歧 2：方案表达 —— 选 C（SSOT + 多视图投影）

**决策**：卡片流仍是拍板面骨架；流程图、时序故事、规则卡、范围对照等作为 SchemeDraft/细模型的**投影**，不单独存储、不可独立编辑（图上批注回写 SSOT 后重新投影）。

- **用户原话**：「同意如上」
- **否决**：B（多视图为主拍板面）——违反 ADR-0014 卡片流定型与「非自由白板」约束；纯 A——外行「看不懂不敢签」的缺口不补。
- **约束**：任一视图必须与 SSOT 一致，不一致以 SSOT 为准并标渲染版本；理解度校验（情景问答）作为可选增强另立卡，不在本次裁决范围。
- **影响**：不改 ADR-0014 卡片流定型；与 `TASK-C.10q` 遗留债及 `docs/rfc/v0.2-multi-agent-pipeline.md` 附录 C（三张真全景卡：业务功能脑图/用户旅程泳道/业务概念图，DEFERRED）对齐——本裁决的多视图投影若落地，应优先复用该附录已锚定的三卡定义，规格卡评审时须处理「附录 C 三卡与蓝图视图清单如何并轨」，不得另起第二套视图体系。

### 分歧 3：确认机制 —— 选 C（工程不变量 + 信任档）

**决策**：ADR-0018 密封内核（快照 + `frozen_quotes` + digest + 失败关闭）不变；其上叠加「信任档」：

- **用户原话（七行勾选）**：「同意如上」
- **用户原话（信任档）**：「同意」——用户确认时选、选择入快照、默认标准档
- **档位**：轻确认（小改动，快照即可）/ 标准密封（现状）/ 重确认（快照 + 逐项勾选 + 可选冷静期）。
- **谁选、如何存证（用户拍板口径）**：由用户在确认时选择，**档位选择本身写入快照存证**；默认档为标准密封；升档随时可，降档仅允许在确认前。
- **否决**：B（商业契约替代密封）——冷静期/变更单是商业语义，不能替换工程密封；纯 A——高代价改动缺少「郑重感」分级。
- **边界**：变更单计价、责任归因、冷静期时长属商业层，本裁决不定，另立产品 RFC。
- **影响**：不改 ADR-0018 密封内核；商业语义层另立。

### 分歧 4：判卷标准 —— 选 C（硬门禁 ∧ 人验）

**决策**：`can_merge` 等机器门禁只由物理证据派生（退出码/哈希/指纹），不可被用户点击或 AI 声明旁路；用户试玩验收是**额外**人工闸门；录屏/截图作为人证留存，不替代退出码。

- **用户原话**：「同意如上」
- **否决**：B（用户勾选为完成标准）——假绿可进；任何弱化硬门禁的变体。
- **影响**：无，现状即此。本条裁决的意义是**明文确认不可 trade-off**。不改 ADR-0005；纯增强。

### 分歧 5：Agent 拓扑 —— 选 A（三实体 + Daemon，Worker 内部可扩展）

**决策**：对外维持搭档 / Supervisor / Worker + Daemon 裁判；Worker 内部允许拆多子 Agent（架构/测试/评审等），但子 Agent 一律无设定权，产出仍经 Daemon 裁决落盘。

- **用户原话**：「同意如上」
- **否决**：B（Orchestrator 多 Agent 平权编排）——裁决权与生成权分离是内核，不可动。
- **影响**：不改 ADR-0014；Worker 内部细分属实现细节，随 v0.2 多 Agent 流水线（已 DEFERRED）一并评估。

### 分歧 6：部署形态 —— 先 A，托管另议

**决策**：维持本地优先 + 合入用户仓库 + 发布到用户自有目标。托管/SaaS 档涉及多租户、计费、责任模型，属产品线级决策，**另立裁决**，本次不定。

- **用户原话**：「同意如上」
- **否决**：C（现在就做部署分级）——托管档前置依赖（多租户隔离、证据落点重设计、商业契约）均未决，现在分级是空头档位。
- **影响**：不改 ADR-0006。

### 分歧 7：Spec 粒度 —— 选 C（粗方案为执行层 + 细领域模型为可选加层）

**决策**：`SchemeDraftV2` 仍是可签执行层与唯一 SSOT；蓝图式细模型（Actor/UseCase/Process/Rule/Screen/AC）作为**可选加层/投影源**，随方案 size 或行业模板开启；**禁止双 SSOT**——细模型若存在，必须从 SSOT 派生或回写 SSOT，二者不一致以 SSOT 为准。

- **用户原话**：「同意如上」
- **否决**：B（细模型替换 SchemeDraftV2）——换掉核心数据模型，密封/合同/证据链全部要重做；纯 A——多视图投影（分歧 2）没有可投影的细内容，C 在分歧 2 处落空。
- **参考**：蓝图 Spec 的通用外壳（`status`/`scope`/`provenance`/`links`/`confidence`）与状态规则（AI 不能设 confirmed、改后回落、基线后 locked）可作为加层设计底稿；其已评审标注的缺口（quote 无哈希、无确认快照实体、测试目标自生成、deprecated 无墓地语义、缺 ChangeOrder 实体）吸收时须补齐而非照抄。
- **影响**：不替换 SchemeDraftV2；禁止双 SSOT。
