# Stagent 文档治理体系规格

> **存档口径**（TASK-J.41a）：`status: draft` / 目标态未激活。本文件是 Stagent 未来给用户项目用的治理能力产品蓝图，不是本仓施工规范；不进 `docs/specs/`、不作施工依据。任何条款不得直接覆盖现行 docs/；吸收只能经 J.41b 逐条反哺。
>
> **编号分家**：本文件 Q-n/S-n 为产品拍板编号，与 scheme-patch-engine.md 的引擎测试锚点 Q-n 编号无关。

## 0. 锚点与约定

**user_said 锚点**（业主原话要点；本规格只引用，不改写、不扩写）：
- U1 用户是有软件开发需求的业务人员，不是技术人员；软件专业工作由 Agent 完成。
- U2 流程：设计师 Agent 生成实施方案 → 施工 Agent 按方案施工 → 用户验收；
  不满意找设计师 Agent 改方案，不直接指挥施工 Agent。
- U3 文档是需求与软件效果之间的翻译载体与合同。
- U4 机器做工序验收，人做最终验收与决策点拍板。
- U5 AI 的推断必须标注，不得冒充用户决策。

**标记约定**：`user_said`（用户原话）/ `user_confirmed`（用户确认）/
`ai_inferred`（AI 推断）/ `machine_auto`（机器生成）。
推断不得冒充决策；机器生成内容不得冒充用户输入。

## 1. 角色与文档载体

| 角色 | 写什么 | 不写什么 |
|---|---|---|
| 用户（业务人员） | brief 原话、approval 确认、final 验收、决策点拍板 | 不写方案、不改施工记录 |
| 设计师 Agent | dialogue 问答、scheme 方案包、change 变更建议 | 不施工、不改 brief 原话 |
| 施工 Agent | build 施工记录、halt 停工单 | 不改方案、不验收 |
| 平台/规则引擎 | gate 机器验收、lint 监理、存证 | 不做业务判断 |
| **AI 技术顾问** | 把技术事实翻译成业务语言、给出建议；建议内容随确认记录一并存证 | 不替用户拍板；建议不得冒充用户决策（建议标 `ai_inferred`，拍板标 `user_said`/`user_confirmed`） |

**AI 技术顾问的定位（Q-15）**：业务用户的技术判断天然委托给 AI——
「用户确认」「用户拍板」的实际执行者是「用户 + AI 顾问」组合。
因此：(a) 确认界面必须假设用户看不懂技术原文，AI 的翻译与建议是
确认流程的一部分，不是附加服务；(b) 防线要防的不只是「AI 冒充
用户决策」，还有「AI 转述失真导致用户拍错板」——所以确认存证
必须包含「用户基于什么 AI 建议拍的板」，否则事后追责时
「用户确认了」是空证。

## 2. 文档文件树（合同单位 = 方案，Q-14）

```
<项目>/
  brief.md      需求原话与材料（user_said 留档；非合同，是追责依据）
  dialogue.md   吸收过程（冲突消解、问答、拍板记录）
  scheme/       统一方案（唯一合同；版本演进 patch/major）
  approval.md   方案确认与哈希
  build/        施工记录（halt.md 停工单、change/ 变更）
  gate.md       机器工序验收
  final.md      整体验收（对完整软件，非对单条需求）
```

**单方案串行（Q-14）**：方案可迭代，同一时刻仅一个生效方案；
新方案在前方案验收或废弃后开启。

**brief 的定位**：用户的模糊需求经 dialogue 吸收进统一方案后，
需求本身「消失」——brief 留原话不是合同，是**追责依据**：
方案执行出问题时回溯「当初用户到底要什么」。

## 3. 标记体系（R1–R8）

- R1 每条事实标来源四态之一；
- R2 `ai_inferred` 不得冒充 `user_said`/`user_confirmed`；
- R3 确认须可追溯到具体条目（confirm_ref + 哈希）；
- R4 方案包版本演进：patch（不弹用户，事后摘要）/ major（弹用户拍板）；
- R5 施工 Agent 可读 brief 原话，但无权据此改方案（Q-5：可读不可改）；
- R6 机器验收只验工序，不替用户做最终验收；
- R7 决策点八类必须弹用户拍板（Q-3）：范围变更 / 已确认条目修改 /
  边界外文件 / 估算超档 / 依赖新增 / 验收标准放宽 / 数据与密钥 /
  规则自修改；
- R8 受托生效（Q-1）：用户确认合同即一次性授权技术细节；
  delegated 条目必须可追溯到已确认 E-n，lint 强制校验该追溯。

## 4. 条目与生命周期（R17、R21、R22）

- R17 条目状态机：proposed → in_dialogue → in_scheme → confirmed →
  delegated → building → verified → accepted；
  任何条目不得跳过 confirmed 直接进 building；
- R21 冲突推断呈现：两个 Agent 对同一条目给出冲突的 ai_inferred 时，
  用户看到冲突卡（两方表述 + 术语表 +「都不对，我来说」出口），
  不得由平台静默择一；
- R22 验收后翻案：`accepted` 永不重开；新 REQ 带 `amends:` 指回旧条目；
  事因三分类「漏检 / 翻译错 / 需求变」由 AI 顾问初判 + 用户拍板；
  处置路径按分类分流。

> **来源（R22）**：`ai_inferred` 重建版——原文在 Claude 会话中截断，按可见内容 + 落点索引重建，与原文可能有出入。终稿正文原先没有 R22 单独条款。上列文字只含本次给出的四点，没有补写分类之后的具体路径。

## 5. 方案包与确认（R20、合入授权点）

- R20 预览机制：用户可要求「先看看效果再决定」——预览不产生确认效力，
  看过满意不等于 confirmed；确认仍须走 approval 显式动作；
- **合入授权点（S-2 澄清）**：「合入」指**施工产物并入主线**，
  不是方案变更并入合同（后者由 approval 覆盖）。规则：
  - patch 类：可自动合入，仅事后摘要告知用户；
  - major 类：必须用户显式授权方可合入；
  - 授权存证：每次合入记录「谁、何时、基于什么检查结果」
    （授权人 / 时间戳 / 关联 gate 结论 / 方案包版本哈希）；
  - patch/major 分类由 lint 复核，误分类按 R19 治理事故处置；
  - 合入授权不可批量——每个方案包的合入单独授权或单独自动。

## 6. 施工与异常（halt、R18、R19、X0–X4）

- halt.md 结构化停工单：现象 / 已试方案 / 需要什么决策 / 阻塞范围；
- R18 halt 超时：T_ack / T_remind / T_park 数值待定（Q-13 暂缓）；
  超时未响应进入提醒节奏，长期未响应转入 parked 不占用资源；
- R19 治理事故（INC-n）：误分类、误放行、转述失真等治理层故障，
  走「登记 → 回滚到回滚点 → 向用户披露 → 追认或保持回滚」流程；
- 异常分级：X0 自修重试（预算默认 3，Q-4）→ X1 工序内处理 →
  X2 弹用户 → X3 拍板 → X4 红线（必须逐项确认，不可批量）。

## 7. 业主拍板记录（user_said）

- **Q-1 受托生效：接受，加边界**——用户确认合同即一次性授权技术细节；
  delegated 条目必须可追溯到已确认 E-n，lint 强制校验该追溯。
- **Q-2 patch 不弹用户：接受**——仅事后摘要；patch/major 分类进 lint 复核。
- **Q-3 决策点清单：接受七类，新增第八类**——「规格/治理规则自身的修改」
  必须弹用户拍板。
- **Q-4 自修重试预算：接受，默认 3**。
- **Q-5 施工 Agent 读原话：可读不可改**——防线在「不能改」不在「不能看」。
- **Q-6 批量确认与红线清单：接受框架，清单待补**——X4 红线具体范围待定。
- **Q-7～Q-10**（v2 阶段拍板）：接受多需求依赖粒度到 E、写范围重叠串行、
  跨需求通知 NT-n、需求清单视图。
- **Q-11 逐项接受 R17–R23**（压力测试修补全部并入正文）。
- **Q-12 依赖新增释义：接受**——外部依赖 + 跨方案 needs。
- **Q-13 R18 数值：暂缓**——机制已接受，数值落地时再定。
- **Q-14 合同单位 = 方案：接受**——需求被吸收为统一方案；单方案串行；
  验收对象为完整软件。
- **Q-15 AI 技术顾问：接受**——技术决策委托 AI 顾问；顾问建议随确认
  记录存证（confirm_ref 增 advisor_ref）；转述失真导致的误确认按 R19
  处置，责任不归用户。
- **S-1 边界变更走拍板**；**S-2 合入授权点**（澄清：指施工产物并入主线）；
  **S-3 原话主权**；**S-4 推断标注强制**。

## 8. 多需求并行治理（远期可选，默认不启用）

> 本章为远期能力预留，默认关闭。单项目单方案为主轴（Q-14）。

- 依赖粒度到 E，默认等对方终验通过后才开工；
- 写范围重叠默认串行，文件级写锁排队，不弹用户；
- 跨方案变更牵连用 NT-n 通知：已验收工序不动，被牵连后续工序
  开工前阻断；
- 用户视角需求清单：哪些在问答 / 哪些在施工 / 哪些在等验收 /
  哪些停工；
- 编号与目录按方案隔离。

## 9. 规则自演进

- 规格/治理规则自身的修改必须弹用户拍板（Q-3 第八类）；
- `in_flight` 处理：规则收紧时，在途条目若命中新决策类别则回落
  待确认——与 Q-1 不冲突（受托授权以「不命中决策点」为前提，
  规则收紧后回落是边界内行为）；
- 规则修改存证：谁提、谁批、何时生效、影响哪些在途条目。

## 10. 红线清单（RL-n，X4 具体范围）

- RL-1 边界外文件写入；
- RL-2 已确认条目修改；
- RL-3 不可逆操作；
- RL-4 外部服务与收费；
- RL-5 数据与密钥；
- （清单待 Q-6 审计后补全；红线条目必须逐项确认，不可批量——R15）

## 11. 批量确认有效性（R15、R23）

- R15 红线条目（带 rl 标记）必须逐项确认，不得并入批量；
- R23 confirm_ref 增 `mode: single|batch` 与 `rl: RL-n|none` 字段；
  有效性新增条件：带 rl 的条目 mode 必须为 single，否则**无效，
  条目自动回落 ai_inferred**（责任在平台，用户不被视为「同意过」）；
  执行面核对 mode 而不只核对存在；已执行的建 INC-n 按 R19 流程处置；
- confirm_ref 增 `advisor_ref` 字段（Q-15）：记录用户确认时基于的
  AI 顾问建议版本，事后可核对「AI 当时怎么说的」与「用户确认了
  什么」是否一致。

## 14. 边界声明

本规格为**理想态产品蓝图**——描述给用户项目用的文档治理能力。
方案是用户侧合同单位（业务用户只见整体）；方案内部执行可由
Agent 自主分解为更细的交付单元，该分解对用户不可见、不影响
本规格的合同粒度定义。
