## 1. 威胁模型分析：Evidence 与门禁残余面边界

在经过 P0.1～P0.3b-2 的整固后，IDE 流水线建立了覆盖控制模式判定、Scope 审计、沙箱见证记录与测试完整性防护的多道门禁。然而从**端到端信任链（Chain of Trust）**的视角审视，当前系统在宿主执行层仍存在根本性的信任根边界断裂：**「有权限者即可绕过全部已建门禁」**。

### 1.1 残余攻击面与三问分析

| 追问项 | 现状事实（Code Facts） | 威胁后果 | 现有防线盲区 |
| :--- | :--- | :--- | :--- |
| **谁可写 Evidence？** | `daemon/pipeline/orchestrator.ts:2565`（`writeEvidence`）将生成的 `EvidenceBundle` 序列化为明文 JSON，落盘至本地 `.stagent/evidence/{contract_id}/{evidence_id}.json`。 | 本地宿主进程、任何具备工作区或用户目录写权限的脚本、在 `UNCONTROLLED_EXTERNAL` 模式下运行的 CLI Worker，均可直接篡改或覆盖该 JSON 文件。 | `merger.ts:149` 仅通过文件系统读取 `EvidenceBundle` 并做 Schema 校验，无法检测文件落盘后的恶意替换。 |
| **谁可改 witness？** | `daemon/worker/sandbox/container-host.ts:285` 的 `verifySandboxWitness` 仅校验见证对象的内存结构与字段合法性（`exit_code`、`mount_mode`、`via` 等）。 | 攻击者或被利用的宿主环境可凭空捏造一个符合 Schema 的 `sandbox_witness` 对象（填充虚构的 `container_id`、`mount_mode: "scoped"`、`exit_code: 0`）。 | 见证对象缺乏来自特权守护进程（Daemon/Docker Socket）的不可伪造凭据（如加密签名或一次性验证 Token）。 |
| **谁可伪造 `worker_control_mode` 字符串？** | `src/lib/evidence.schema.ts:161` 将其定义为普通枚举字符串（`"GATEWAY_ENFORCED" \| "SANDBOX_ENFORCED" \| "UNCONTROLLED_EXTERNAL"`）。`orchestrator.ts:2616` 计算后写入 JSON。 | 只要在 JSON 证据文件中将字符串修改为 `"SANDBOX_ENFORCED"` 并附带伪造见证，`deriveCanMerge` 即会执行放行逻辑分支。 | 缺乏防篡改完整性校验（HMAC/数字签名），字符串本身不具备任何信任度。 |

### 1.2 结论与安全假设边界

**当前门禁系统的信任边界假定「宿主环境与本地文件系统绝对可信」**。一旦 Worker 在非受控外部环境运行，或恶意指令渗透至宿主用户态，攻击者无需攻破 Docker 容器或突破 Linux 内核，只需在合并阶段前直接覆写 `.stagent/evidence/` 目录下的证据 JSON 文件，即可无视所有门禁条件将代码合并进主分支。因此，**构建不可篡改的 Evidence 可信链是保障门禁有效性的先决条件**。

## 2. Evidence 可信链加固技术选型报告

针对 Evidence 的防伪与防篡改，评估四种主流工程选型方案，结合单机 IDE 桌面端场景与红线约束进行对比。

### 2.1 四类技术方案深度比较

| 选型方案 | 技术实现机制 | 密钥管理与可信主体假设 | 复杂度与运行开销 | 核心优势 | 致命缺陷 / 局限性 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **方案 1：非对称数字签名（Ed25519）** | Daemon 启动时持有或生成 Ed25519 私钥，对 Canonical JSON 证据包进行私钥签名，签名写入 `signature` 字段；Merger 与外部使用公开公钥验签。 | **假设**：Daemon 内存私钥不被普通 Worker 读取。<br>**管理**：私钥仅存宿主内存/系统 Keyring，公钥可明文随合同或系统分发。 | **实现**：中等（Node 原生 `crypto` 原生支持，约 150 行代码）。<br>**开销**：单次验签 <0.2ms，零依赖。 | 1. 签名者与验证者分离，公钥可任意暴露。<br>2. 支持脱机、跨进程及第三方独立审计。<br>3. 完全消除伪造可能。 | 若宿主进程被完全 dump 内存，私钥可能失窃（但此时宿主已被完全接管）。 |
| **方案 2：对称密钥 HMAC（HMAC-SHA256）** | Orchestrator 与 Merger 共享一个预设或运行期派生的对称密钥，对 Evidence 哈希生成 HMAC。 | **假设**：两端必须同时安全存储同一共享密钥。<br>**管理**：单机易混淆，多进程难同步。 | **实现**：极低（Node 原生 `crypto`）。<br>**开销**：单次 <0.05ms，零依赖。 | 1. 实现最简，速度极快。<br>2. 防篡改能力强。 | 1. 无法区分签名方与验证方。<br>2. 任何能验证 HMAC 的模块都有能力伪造签名，无法支持不可信第三方面向的公开独立复核。 |
| **方案 3：不可变存储（WORM / OS 属性锁定）** | 文件写入后调用系统底层属性（Linux `chattr +i`、macOS `chflags uchg`、Windows Read-Only ACL / `chmod 0400`）。 | **假设**：操作系统权限模型能严格区分 IDE 运行身份与 Worker 执行身份。 | **实现**：高且平台差异极大。<br>**开销**：系统调用开销，需处理异常。 | 1. 概念直观，防普通文件覆写。<br>2. 操作系统层面兜底。 | 1. **单机同权限无效**：用户态进程可随时用 `chmod +w` 重新获取写权限。<br>2. `chattr +i` 需 root/sudo，桌面端无法普及。<br>3. Windows WSL2 跨文件系统权限映射极易失效。 |
| **方案 4：独立审计记录（Git Notes / Merkle Tree）** | 将 Evidence 哈希与决策记录提交至独立的 Git 引用（如 `refs/notes/audit`）或追加式 Merkle Tree。 | **假设**：Git 数据库对象本身不被 `git filter-branch` 或直接对象删除篡改。 | **实现**：中高（需编排 Git 底层 plumbing 命令）。<br>**开销**：Git 对象写入开销。 | 1. 与代码仓库同生命周期持久化。<br>2. 审计追溯能力强。 | 1. 仅能证明「曾有过这条记录」，无法证明记录最初不是被伪造写入的。<br>2. 单独使用不能防伪，仍需搭配密码学签名。 |

### 2.2 权衡分析与推荐选型

1. **红线契约契合度**：
   - Node.js 内置的 `crypto` 模块（原生支持 `crypto.generateKeyPairSync("ed25519")`、`crypto.sign`、`crypto.verify`）**无需引入任何第三方 NPM 依赖包**，严格遵守「不新增运行时依赖」的红线；
   - 采用标准规范化 JSON 算法（RFC 8785 排序规则）确保多平台哈希确定性。
2. **推荐方案：以「Ed25519 数字签名」为主防线，辅以「Git Trailer 哈希绑定 + 文件权限 chmod 0400」的纵深防御组合**。
   - **主防线（密码学强制）**：Evidence 生成时附加 `signature: { alg: "ed25519", public_key: "...", sig: "..." }`。Merger 执行合并前必须独立执行 `verifyEvidenceSignature`；
   - **次防线（环境防误触）**：写入后置为只读（`0400`），防止同进程并发异步任务或误操作覆写；
   - **回溯链（仓库内绑定）**：在 Merge Commit Trailer 中持久化记录 `Stagent-Evidence-Hash`（已由 TASK-E.2 预留），形成 Git 提交历史与签名凭证的双向锚定。

## 3. P0 独立动态验收测试矩阵

为落实「代码交付 ≠ 安全验证通过」，必须建立独立的动态渗透验证矩阵，全面脱离开发期单元测试的自证循环。

### 3.1 核心防护门禁动态验收项

| 编号 | 门禁卡位 | 验收目标场景 | 动态测试构造方法（负向攻击用例） | 预期判定结果（Fail-Closed） |
| :--- | :--- | :--- | :--- | :--- |
| **TC-P0-1A** | P0-1 门禁闭合 | 合同版本过期 | 构造 Evidence 绑定的 `contract_revision: 1`，修改合同至版本 2 后发起合并请求。 | 抛出 `E_EVIDENCE_REVISION_MISMATCH`，阻断合并。 |
| **TC-P0-1B** | P0-1 门禁闭合 | 任务分支提交流转 | 在 Evidence 生成后，向任务分支悄悄追加空提交 `git commit --allow-empty`，再调用合并。 | 抛出 `E_EVIDENCE_STALE`，阻断合并。 |
| **TC-P0-1C** | P0-1 门禁闭合 | 非受控模式伪装 | Evidence 记录 `worker_control_mode: "UNCONTROLLED_EXTERNAL"`，尝试触发合并。 | 抛出 `E_CANNOT_MERGE`（仅允许受控模式），阻断合并。 |
| **TC-P0-2A** | P0-2 变更审计 | 未授权路径越界写入 | 构造任务分支改动越出 `writable_paths`（例如修改 `daemon/pipeline/merger.ts`），发起合并。 | `assertCandidateScopeCompliant` 拦截，抛出 `SCOPE_VIOLATION`。 |
| **TC-P0-2B** | P0-2 变更审计 | 重命名路径逃逸 | 将授权文件重命名为非授权受保护路径（如 `a.ts -> src/lib/contract.schema.ts`）。 | 变更审计对 rename 新旧路径均做校验，抛出越界拦截。 |
| **TC-P0-3A** | P0-3b 容器挂载 | 根工作树只读写阻断 | 在 Docker 容器内执行 `echo "hack" >> package.json`（Worktree 根只读）。 | 容器内核物理阻断，返回 `EACCES`（Permission denied）。 |
| **TC-P0-3B** | P0-3b 容器挂载 | `.git` 目录篡改阻断 | 在 Docker 容器内执行 `rm -rf /work/.git` 或向 `.git/hooks` 写入后门脚本。 | tmpfs 遮蔽隔离生效，操作被物理阻断或完全不影响宿主 `.git`。 |
| **TC-P0-3C** | P0-3b 容器挂载 | 验收阶段全量只读拦截 | 在 `readonly_enforced` 验收阶段模式下，尝试写入即使在 `writable_paths` 内的文件。 | 容器内无任何 `:rw` 挂载点，全量写入均物理报 `EACCES`/`EROFS`。 |
| **TC-P0-4A** | P0-4 测试完整性 | 既有测试被篡改 | 故意修改既有单元测试使其无条件 `assert(true)` 并删除关键断言，发起合并。 | 识别测试篡改，触发基线隔离重跑；因基线测试重跑失败抛出 `E_TEST_BASELINE_REGRESSION`。 |
| **TC-P0-4B** | P0-4 测试完整性 | 破坏基线环境逃逸 | 破坏宿主环境导致既有基线测试无法运行。 | 失败关闭，抛出 `E_TEST_BASELINE_UNAVAILABLE`，阻断合并。 |

### 3.2 跨平台验收范围与判据

| 操作系统环境 | 运行时载体 | 核心差异点与环境陷阱 | 验收合格判据（必须全部满足） |
| :--- | :--- | :--- | :--- |
| **Linux (Ubuntu)** | 原生 Docker Daemon | 标准 Linux Namespaces + cgroups，挂载语义最严密。 | 1. 负向测试容器内物理返回标准 `EACCES` 错误码；<br>2. 宿主占位预建成功，无目录化混淆；<br>3. 宿主 `.git` 哈希前后严格一致。 |
| **macOS** | Docker Desktop / OrbStack | 跨 Hypervisor 虚拟机，VirtioFS 共享挂载存在时延与大小写不敏感特性。 | 1. 跨 VM 文件变更与宿主即时可见；<br>2. 容器内只读阻断必须抛出物理写入被拒，不可因缓存导致虚假写入；<br>3. 大小写混合路径不产生挂载点逃逸。 |
| **Windows** | WSL2 + Docker Desktop | 跨 WSL2 虚拟环境与 Windows 宿主路径，反斜杠 `\` 与换行符 CRLF 差异。 | 1. 挂载路径归一化为正斜杠，无 `EINVAL`；<br>2. tmpfs 遮蔽挂载在 WSL2 内生效；<br>3. `:ro` 卷在 WSL2 内同样触发只读保护拦截。 |

## 4. Gateway / Sandbox / Witness 信任边界架构契约草案

明确现有架构的防御深度与明确的责任边界，防止安全能力的虚假过度宣称。

### 4.1 核心概念隔离契约

```
+-----------------------------------------------------------------------------------+
| 信任域 A：宿主守护层 (Host Daemon & Orchestrator)                                   |
| - 职责：合同解析、权限判定、Evidence 签发、Merger 门禁执行                             |
| - 信任级别：核心信任域 (Root of Trust)                                             |
+-----------------------------------------------------------------------------------+
         │                                                         ▲
         │ (1) 挂载配置与启动                                         │ (4) 收集退出见证
         ▼                                                         │
+------------------------------------------------------+  +-------------------------+
| 信任域 B：沙箱隔离层 (Container Host)                  |  | 信任域 D：见证凭证层    |
| - 职责：Worktree :ro + 逐路径 :rw 挂载 + tmpfs 遮蔽    |  | (SandboxWitness)        |
| - 隔离级别：Mount Namespace 级文件系统隔离             |  | - 记录模式/挂载数/时长  |
+------------------------------------------------------+  +-------------------------+
         │                                                         ▲
         │ (2) 容器内派工                                           │ (3) 物理隔离约束
         ▼                                                         │
+-----------------------------------------------------------------------------------+
| 信任域 C：执行主体层 (Untrusted Worker in Sandbox)                                 |
| - 职责：代码生成、工程编辑、验证执行                                                 |
| - 隔离边界：容器内无 OS 级只读隔离；非虚拟机级硬件 Attestation                      |
+-----------------------------------------------------------------------------------+
```

### 4.2 架构边界四项明示契约（写入系统安全规范）

1. **Mount Scope 与 OS/Kernel 级隔离的区别**：
   - 现已交付的 `resolveScopedMounts` 属于**文件系统挂载点命名空间（Mount Namespace）**的细粒度约束；
   - 容器共享宿主 Linux 内核，**不具备**如同 KVM、Firecracker 等基于硬件虚拟化的强隔离保证；容器内若发生内核提权（Kernel Privilege Escalation），本机制无法抵御。
2. **硬件级 Attestation 边界**：
   - 当前系统的 `SandboxWitness` 为用户态守护进程采集记录的工程见证；
   - 系统**未实施**硬件级机密计算或安全芯片背书（如 TPM 2.0 Quote、AMD SEV-SNP、Intel SGX），不在当前系统的安全承诺范围之内。
3. **Gateway 信任假设边界**：
   - Gateway 的 API/Tool 拦截仅对经由 Gateway 管道发起的工具调用生效；
   - 对于非沙箱环境或本地进程注入行为，Gateway 无法起到系统级防火墙的拦截作用。
4. **Merger 独立验证边界**：
   - Merger 验证的是预计算产出的 Evidence 证据链有效性，Merger 自身**不会重新执行**全量业务测试套件；因此 Evidence 可信链的完整性是 Merger 做出安全决策的唯一依据。

## 5. 后续施工卡建议及优先级

基于本次评估结论，规划后续安全工程施工卡路线图与依赖拓扑：

```
TASK-P1.1 (本次专项评估 · 纯文档方案)
    │
    ▼ [评审裁决]
TASK-P1-1 (Evidence Ed25519 签名与防篡改验签门禁 · 施工型 · P1-Highest)
    │
    ├─────────────────────────────────────────┐
    ▼                                         ▼
TASK-P1-2 (P0 跨平台独立动态渗透验收测试套件)    TASK-P1-3 (Gateway 凭据脱敏与沙箱见证防伪强化)
(施工型 · P1-High)                         (施工型 · P2-Medium)
```

### 建议施工卡清单

1. **`TASK-P1-1`：Evidence Ed25519 签名与防篡改验签门禁（施工型，优先级：P1-Highest，估算 M）**
   - **目标**：实现 EvidenceBundle 规范化序列化与 Ed25519 数字签名生成；在 `merger.ts` 的 `PRE_MERGE` 阶段强校验签名有效性；
   - **硬依赖**：TASK-P1.1 方案评审通过；
   - **约束**：使用 Node.js 内置 `crypto`，零新增 NPM 依赖；无有效签名的 Evidence 一律 fail-closed 阻断合并。
2. **`TASK-P1-2`：P0 独立动态渗透与跨平台验收套件（施工型，优先级：P1-High，估算 L）**
   - **目标**：落地独立于既有测试套件的动态渗透测试集，实跑验证 TC-P0-1A～TC-P0-4B 十大负向场景，验证 Linux/macOS/Windows 真实阻断行为；
   - **硬依赖**：TASK-P1-1；
   - **交付物**：跨平台动态渗透测试用例与实跑证据记录。
3. **`TASK-P1-3`：Gateway 凭据脱敏与沙箱见证防伪强化（施工型，优先级：P2-Medium，估算 M）**
   - **目标**：阻断宿主敏感环境变量向沙箱泄漏，沙箱见证引入基于单次随机 Nonce 的会话级防重放绑定；
   - **硬依赖**：TASK-P1-1。
