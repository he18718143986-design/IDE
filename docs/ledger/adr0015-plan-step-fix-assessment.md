# ADR-0015 主链计划环节修复评估（只读 · P-276）

> **地位**：只读评估。不改产品代码，不立施工卡。  
> **基线**：`main` `fd36ff5ec221dde534b57f3912bbcce6ddb4db19`（[#352](https://github.com/he18718143986-design/IDE/pull/352) P-275 合入后）。产品代码与 J.49 施工 `b4fecdc09396c1b3654a0fcb8e9d7354d51b8a11` 相同。  
> **依据**：[`adr0015-plan-step-breakpoint.md`](./adr0015-plan-step-breakpoint.md)（P-275）。  
> **标记**：下列修法判断与建议均标 `ai_inferred`，不是施工授权。  
> **授权**：Tina t1344u，在 #352 合入后开独立 docs PR。

## 要修的是什么

P-275 断点：有了可审阅方案、确认按钮也可点之后，走不过「先看到项目计划和里程碑，再按合同确认开工」。生产界面从不调用分解；中栏「确认方案」按 C.22 直接冻结、签一份合同、拉起 Worker。定性是主链顺序与 ADR-0015 不符：一环被绕过了，不是某环坏了。

## 候选 i. 确认方案之后先出计划，再按合同确认开工（建议）

`ai_inferred`。贴 ADR-0015 原口径，也与 ADR-0018、ADR-0019 一致。

- ADR-0015 决策第 2、4 条：计划由方案分解得到；每份合同单独「确认开工」与「合入」。计划本身不是授权凭据。
- ADR-0019 决策第 2、6 条：顺序是可编译方案 → 用户「确认方案，开始规划」→ 密封（ADR-0018）→ PAB → 项目计划 → 合同桩 → 用户「确认开工」→ Worker。「开始规划」不等于「确认开工」，这一下**不**授权 Worker。
- ADR-0018 对照表：密封发生在「开始规划」或 tiny「确认开工」的冻结阶段；合同施工授权另计「确认开工」。

**改动面**：

- 底部「确认方案」只负责冻结方案，并开始规划：走 C.22 的 `CLAIM_AND_QUIESCE`、`VALIDATE_CONFIRMATION`、`FREEZE_SNAPSHOT`，然后由生产 UI 调用 `decomposeProjectPlan`（`src/lib/daemon-api.ts` 第 1321–1345 行），再 `refreshProjectPlan` 让中栏画出项目地图。此路径不签署合同、不 `runWorker`。
- 按钮与说明从「确认后冻结 Spec 并直接开工写代码」（`SchemeReviewPane.tsx` 第 7、846–847 行）改为与 ADR-0019 一致的「确认方案，开始规划」。
- 地图「确认开工」（`ProjectMapPane.tsx` 第 162 行；`handleProjectMapConfirmStart`，`index.tsx` 第 1855–1867 行）继续走现有完整确认事务：预检该合同桩后，再 `SIGN_AND_PREPARE` 并在成功后 `runWorker`。

**与 C.22 五阶段 / 合同粒度的关系**：五阶段不用删。底部按钮不再一次跑完「冻结 + 签署 + 开工」；签署与施工准备改由合同桩上的「确认开工」触发。合同粒度回到计划里的每一份桩，而不是整份方案签成一份合同。`standard` 通常是单里程碑单桩（`decompose.ts` 第 310–329 行，零模型），用户会多点一次「确认开工」。

**风险**：

- 分解器要求 ready 的架构基线（PAB）。`decompose.ts` 第 165–188、301–302 行，缺了就 `E_PAB_NOT_READY`。HTTP 入口未传入时把 `pab` 置为 `null`（`daemon/server.ts` 第 5556 行）。现有 `/api/baseline`（`daemon/server.ts` 第 6318–6367 行）是扫描/认可参考基线，`grants_construction=false`，并不是分解器要的 `ReadyPabView`。只接线 `decompose`、不处理 PAB，会立刻失败。P-275 因界面尚未调用分解，没有把这道门写成断点；本评估把它标为候选 i 落地时必须一起看的前置。
- 现有交接文案和测试把「确认方案」写成「冻结并开工中」「正在准备开工」。拆开后要改这些文案与幂等键（`confirmation_id` 要区分「规划提交」和「开工提交」）。
- `size_hint === "large"` 的分解需要模型客户端（`decompose.ts` 第 332–339 行）。没有注入时会「这个需求我还没拆好」。本评估不处理 large 的模型接线。

## 候选 ii. 维持「确认即开工」，把计划生成并入冻结后流程（不建议作为默认）

`ai_inferred`。C.22 几乎不动：底部「确认方案」仍一次冻结、签署、拉 Worker；只在冻结成功或 `COMMIT` 之后补一次分解并刷新地图。

**改动面**较小：主要是 `handleConfirmScheme` 成功路径上补 `decomposeProjectPlan` + `refreshProjectPlan`，中栏事后出现项目地图。按钮说明可以不改。

**与 C.22 五阶段 / 合同粒度的关系**：五阶段仍表示「确认 = 签署并开工」。计划变成开工之后的投影，不是开工前可审阅的对象。合同仍可能是整份方案一份，和计划里可能出现的多份桩对不上。这要改 ADR-0015 决策第 4 条，也和 ADR-0019「开始规划 ≠ 确认开工」冲突。

**风险**：用户还没看见计划就已经开工；若分解出多份桩，已签署的那一份合同与计划不一致；把「少点一次」换来规格口径改写，后续合同粒度会乱。除非另行拍板改 ADR，否则不作为默认修法。

## 候选 iii. 其他

`ai_inferred`。

- **按钮更名，语义仍是 i**：把底部按钮写成 ADR-0019 原文「确认方案，开始规划」。这是候选 i 的文案，不单独立成一套修法。
- **按 `size_hint` 分流**：`tiny` 不建计划、可走 Fast Path「确认开工」（`docs/specs/project-decomposition.md` 第 20 行；ADR-0018 对照表允许 tiny 在确认开工时冻结）。`standard` / `large` 仍走候选 i。这是候选 i 的范围限定，不是第三条主修法。当前走查里的「登录页」按 `standard` 处理，不能用 tiny 绕过。
- **确认方案之前就分解**：与 ADR-0019「先密封，再 PAB，再计划」冲突，不建议。

## 建议

`ai_inferred`：采用候选 i。让「确认方案」回到「冻结并开始规划」，计划出现后再按合同桩「确认开工」。C.22 的签署与拉 Worker 留在地图确认开工。落地时必须同时面对 PAB 前置，否则分解会在 `E_PAB_NOT_READY` 停下。

本评估不立施工卡，不改 ADR，不改产品代码。若要按候选 i 立卡或按候选 ii 改 ADR，须另点名。
