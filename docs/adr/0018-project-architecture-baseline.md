# ADR-0018: 项目级架构基线必须先于大型项目分解与合同施工

- **状态**：PROPOSED（随本 PR 合入生效）
- **日期**：2026-10-30
- **范围**：`docs/` 规范；不改实现代码
- **依据**：`delivery-path-audit.md` 的 S3/S4 断点；ADR-0015、ADR-0016；项目分解与技术设计规格
- **权威正文**：[项目架构基线规格](../specs/project-architecture-baseline.md)

## 背景

现行链路先由 Scheme 表达意图，再由 ProjectPlan 拆合同桩；合同进入执行后才生成合同级 DesignNote，知识库则随合同合入更新。于是整个项目没有施工前的技术基线来统一模块边界、数据所有权、跨合同接口、依赖方向与架构不变量。

项目分解 D-7 只在分解器显式识别多个合同共享新接口时要求 `interface_first` 桩，无法证明所有共享接口都被发现，更不裁定已有接口兼容、数据所有权和跨合同职责。单份 DesignNote 在计划与合同签署之后生成，视野不足以约束彼此隔离施工的合同。即使每张任务卡满足 DoR、局部测试全通过，整体仍可能因接口不兼容、数据模型冲突或依赖方向不一致而无法组合。普通 Worker 按卡施工不能替项目作出这些全局架构选择。

## 候选脑力瓶颈评估（强制单选）

| 排名 | 候选 | 致命性与裁定 |
|---|---|---|
| **1** | **项目级架构基线缺失：方案/项目计划到跨合同一致系统之间没有施工前的全局技术约束** | **唯一榜首。** 每个合同可局部正确却整体不互操作；事后加测试或按卡施工无法替代模块所有权、接口兼容、共享数据与演进策略的架构裁定。必须在项目分解前定型。 |
| 2 | 意图编译失真：遗漏原话或错误化解冲突 | 会污染下游，但 Supervisor 已有原话锚定、证据台账、SchemePatch 确定性裁决和黄金对话测试，可逐步验证修正。 |
| 3 | 项目分解遗漏依赖或接口先行桩 | 现有 DAG、D-7 与校验规则提供部分护栏；真正盲点是缺少全局架构基准来检验分解器是否识别正确。由榜首基线约束，不另选。 |
| 4 | 测试义务与独立验证不足 | 会放过缺陷，但验证规格已规划红绿义务、证据、真实预览；逐合同可补测，不能修复方向错误的系统架构。 |
| 5 | 发布、知识沉淀与反馈闭环不完整 | 会影响上线和维护，已有各自生命周期规格；属于架构确定后的交付闭环，不能替代架构基线。 |

**为什么不是“把任务卡写得更细”**：DoR 使任务局部可执行，却无法推导全项目模块职责、接口兼容、数据事务和迁移策略。需要有架构责任者在施工前提出可追溯决定，由确定性门禁检查引用、覆盖与版本一致性；模型仅提案，不自评为真。

## 决策

1. 每个 `standard` / `large` 项目，在生成或批准 ProjectPlan 之前必须生成并通过校验 Project Architecture Baseline（PAB，项目架构基线）。`tiny` Fast Path 可跳过完整 PAB；一旦触及跨模块接口、数据/迁移、依赖、安全边界或持久化，必须升级为至少 `standard`。
2. 顺序固定为：可编译 Scheme → 仓库事实与 PAB → ProjectPlan → ContractStub → ScopePlan / 用户确认开工 → 合同级 DesignNote → Worker。PAB 缺失、过期、结构校验失败或存在阻断级未决项时，不得产生可签署合同桩。
3. PAB 定义项目级模块、接口、数据所有权、依赖方向、关键决策、不变量和验证策略；DesignNote 只在 PAB 边界内细化单合同实现。DesignNote 必须引用 PAB 修订和 digest；改变公共边界须先提交 PAB 补丁。
4. Supervisor 对架构方案与取舍负责；模型输出是提案，Daemon 对 Schema、覆盖、引用、版本、新鲜度和跨文档一致性作确定性校验。所有断言标出 `observed`、`user_said`、`user_confirmed` 或 `ai_inferred` 来源。推断不得伪装成用户事实。
5. PAB 不是写权限、密钥授权或开工批准。既有「确认开工」、ScopePlan、保护清单、预算和验证门禁不变；不可逆、费用、安全、外部服务、数据删除等升级项仍按 ADR-0016 交用户裁决。

## 后果

- ProjectPlan、ContractStub 与 DesignNote 增加对 PAB `baseline_id`、revision、digest 的引用；交付主干须把 PAB 放在分解之前。
- PAB、合同级 DesignNote、随代码更新的 `docs/system/` 建立版本链：前者定全局边界，后者细化施工，知识库记录合入后的事实。
- `standard` / `large` 项目增加一次架构分析和校验成本；tiny 单模块改动仍轻量。
- PAB 使架构责任与证据可审查，不等于证明架构正确。正确性仍由接口/集成测试与用户验收验证。

## 本 ADR 的验收条件

- [ ] PAB Schema、必需字段、门禁、版本失效、合同引用和测试矩阵写入权威规格。
- [ ] 主干、项目分解、DesignNote 与相关施工卡都指向同一 PAB 前置规则。
- [ ] 明确 PAB 是架构约束，不是施工授权；Worker 不负责全局架构裁决。
