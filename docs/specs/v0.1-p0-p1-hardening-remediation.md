# Stagent v0.1 P0/P1 Hardening Remediation Specification

> Status: proposed contract-ready specification  
> Scope: convert the Stagent v0.1 special review into bounded, independently verifiable remediation work.  
> This document is not proof that any remediation has been implemented or tested.

## 1. Goal and non-goals

Goal: improve assurance that execution isolation, independent acceptance, Evidence trust, and merge adjudication behave as designed, while preserving Stagent's contract-first workflow.

Non-goals:
- Claiming Stagent is a hostile-code security sandbox or formally security-certified.
- Replacing the existing Contract / Worktree / Evidence / Merger architecture.
- Weakening existing controls to make tests pass.
- Treating UI state, Worker statements, or self-reported logs as authorization or acceptance.
- Executing tests against real secrets, production systems, or unsafe external targets.

## 2. Priority and deliverable breakdown

### P0-A — Execution Assurance and policy-to-runtime binding

**Objective:** distinguish application-level restrictions from verified runtime isolation and bind assurance to the actual execution configuration.

Requirements:
1. Make the selected execution assurance tier explicit in the Contract and execution record: L0 local child-process (trusted/low-risk), L1 constrained runtime (where supported), or L2 container/VM-backed isolation (for untrusted/high-risk work). Do not imply a higher tier unless the backend was actually selected and attested.
2. Bind execution record to backend identity/version, policy/config fingerprint, target platform, session/worktree identity, and timestamp.
3. Fail closed on missing, mismatched, stale, or unverifiable runtime attestations whenever a Contract requires a tier above L0.
4. Ensure command-template execution and Worker-added commands both pass the same authorization boundary. Contract verification commands are not an implicit bypass.
5. Make tier limitations visible in Evidence and user-facing delivery status; do not label application-layer fences as OS isolation.
6. Test policy consistency and failure behavior using safe fixtures and controlled mock/integration environments.

**Acceptance criteria (P0-A):**
- [ ] Contract tier is explicit and schema-validated.
- [ ] Execution Evidence contains backend, tier, policy fingerprint, platform, session binding, and attestation status.
- [ ] Required-tier mismatch, missing attestation, stale attestation, or unavailable backend produces BLOCKED (not PASSED).
- [ ] Both fixed Contract commands and Worker-added commands are authorized, recorded, and subject to policy.
- [ ] Tests establish that UI presentation state cannot elevate execution permissions.
- [ ] Documentation accurately distinguishes Worktree, process constraints, and OS isolation.
- [ ] CI runs applicable checks; platform limitations are recorded, not silently skipped.

### P0-B — Independent Acceptance and protected baseline

**Objective:** acceptance criteria and test baselines cannot be unilaterally changed by the implementation Worker, and acceptance reruns are bound to the exact candidate.

Requirements:
1. Store baseline test assets, runner configuration, acceptance criteria, and baseline fingerprint under Daemon-controlled or otherwise separately protected ownership.
2. Record baseline version/fingerprint and candidate fingerprint in acceptance Evidence.
3. Detect changes, additions, removals, renames, skips, weakening indicators, and restore failures in baseline assets/configuration; uncertain detection must not produce PASS.
4. Run baseline acceptance independently from Worker-added tests where practical. If independence cannot be established, record BLOCKED/limited assurance.
5. Ensure restore/recovery failure blocks PASS and merge eligibility.
6. Require review of changes to acceptance criteria or baseline by a role/process independent from the implementation session.

**Acceptance criteria (P0-B):**
- [ ] Baseline ownership and version are explicit and not writable through the Worker-authorized path.
- [ ] Evidence records baseline fingerprint/version and candidate fingerprint.
- [ ] A modified, missing, or unrecoverable baseline fixture yields BLOCKED or FAILED and prevents merge.
- [ ] Worker-added tests are identified separately; acceptance does not rely solely on Worker-authored tests.
- [ ] Restore failure and incomplete rerun cannot be represented as PASSED.
- [ ] Acceptance criteria changes require a separately recorded approval.
- [ ] Acceptance runs identify runner, environment, inputs, and result.

### P1-A — Evidence signing trust-root and verification policy

**Objective:** signatures establish integrity and a clearly defined signer trust relationship, not merely self-consistency.

Requirements:
1. Define trust levels: embedded/self-declared key, pinned local key, authorized signer, and external trust anchor (where available). UI and Evidence must not conflate these levels.
2. Merger must obtain trust policy from an independent trusted configuration/registry, not solely from Evidence's own key claim.
3. Bind signed payload to contract ID/version, session, candidate fingerprint, acceptance record, runtime attestation, and relevant execution metadata.
4. Reject signature verification over incomplete, stale, mismatched, or unsupported payload versions.
5. Document key generation, rotation, revocation, storage, backup/recovery, and compromised-key handling. Avoid exposing private keys in logs or Worker context.
6. Keep local audit hash chains described as integrity checks against accidental modification unless a separate trust anchor prevents an attacker from recomputing them.

**Acceptance criteria (P1-A):**
- [ ] Trust level is explicit and reflected in merge policy.
- [ ] Merger uses a trusted key/policy source independent of Evidence claims.
- [ ] Signed payload binds all required identity and integrity fields.
- [ ] Wrong-key, stale-payload, altered-payload, unsupported-version, and trust-policy failure tests reject acceptance.
- [ ] Key lifecycle and audit-record threat model are documented.
- [ ] UI wording does not claim immutable audit or identity proof without a corresponding trust anchor.

### P1-B — Merge transaction, race, and recovery audit

**Objective:** ensure all merge paths recheck the complete authorization and evidence state at the critical boundary and recover safely from interrupted delivery.

Requirements:
1. Inventory every merge, retry, resume, recovery, and alternate entry point.
2. Apply a single auditable gate to each path, including Contract state/approval, Evidence schema/version/signature, candidate fingerprint, scope audit, test integrity, runtime attestation, worktree state, and lock/state constraints.
3. Recheck candidate identity immediately before merge; make checks and merge operation transactionally consistent or detect/reject intervening changes.
4. Define lock ownership, expiry, contention, and recovery semantics; avoid silent lock bypass.
5. Define post-merge verification, rollback/compensation boundaries, archive semantics, and interruption handling.
6. Produce a structured rejection reason and Evidence record for failed gate conditions.

**Acceptance criteria (P1-B):**
- [ ] Merge-entry-point inventory is complete and reviewed.
- [ ] Every entry point is proven to invoke the shared gate.
- [ ] Candidate changes between check and merge cause rejection or a complete revalidation.
- [ ] Lock/retry/resume tests demonstrate deterministic safe outcomes.
- [ ] Interrupted merge recovery is documented and tested using isolated fixtures.
- [ ] Failed gate decisions are recorded with machine-readable reason codes.
- [ ] No bypass is available via UI state or direct Worker action.

### P1-C — Cross-layer invariants and state projection

**Objective:** keep lifecycle, delivery state, evidence status, and presentation projections consistent without making UI a security authority.

Requirements:
1. Document authoritative ownership for each state field.
2. Define invariants and transitions in a central table.
3. UI projections are derived and cannot authorize execution, verification, or merge.
4. Invalid or contradictory states fail closed and are surfaced for recovery.
5. Add independent matrix tests for valid/invalid state combinations, transitions, and recovery branches.

**Acceptance criteria (P1-C):**
- [ ] Invariants map each authoritative field to its owner.
- [ ] Projection mismatch blocks sensitive transitions or triggers deterministic repair.
- [ ] Matrix tests cover transition guards and contradiction cases.
- [ ] Presentation state cannot change Contract approval, execution tier, or merge eligibility.

## 4. Evidence contract

Each remediation run must produce a machine-readable Evidence bundle and a human-readable summary. Required fields (adapt to current schema without duplicating authoritative data):

- spec_id: this remediation specification identifier and version
- task_id: P0-A, P0-B, P1-A, P1-B, or P1-C
- contract_id, contract_version, approval reference
- worker_session_id, worktree identifier, candidate HEAD and candidate fingerprint
- baseline identifier/version/fingerprint (for acceptance work)
- runtime tier, backend identity/version, policy fingerprint, platform, attestation result (for execution assurance work)
- verification commands and normalized outcomes, duration, exit status
- test matrix IDs, results, skipped/blocked reasons
- changed paths and scope audit summary
- signature verification result and trust level
- merge gate outcome, reason codes, and timestamps
- tool/environment versions needed to reproduce
- redaction status; no raw secrets, tokens, or sensitive environment values

Evidence must not claim PASSED when required fields are missing, checks were not run, results are stale, or verification cannot be independently established. Unknown/unavailable must be explicit, not coerced to success.

## 5. Contract-driven execution sequence

1. Read this specification and repository-specific runtime/safety contracts.
2. Supervisor produces a ScopePlan listing tasks, paths, invariants, commands, test IDs, risk, and required assurance tier.
3. Human approves the frozen Contract. Do not start implementation before approval.
4. Execute one task at a time in a bounded Worktree; use the minimum required permissions.
5. Run tests mapped to the task. Do not modify acceptance baselines to make tests pass.
6. Collect Evidence against the exact candidate fingerprint.
7. Independent review checks acceptance criteria and Evidence completeness.
8. Merger rechecks gates; merge remains human-authorized as defined by existing project policy.
9. If a criterion fails or is uncertain, report BLOCKED/FAILED and create a follow-up Contract; do not self-waive.

Suggested task order: P0-A and P0-B first; P1-C alongside foundational changes only if needed; P1-A after the payload/binding inventory; P1-B after gate-entry inventory. Re-plan if dependencies or scope change.

## 6. Definition of Done

- All acceptance criteria for the selected task are met and independently reviewed.
- Relevant test matrix rows pass; unavailable checks are explicitly BLOCKED with justification and cannot be silently treated as PASS.
- Evidence binds the results to the exact Contract, candidate, baseline, runtime configuration, and trust policy.
- Scope audit is clean or explicitly approved through a separate Contract.
- No regressions in existing lifecycle, safety, authorization, and delivery tests.
- Documentation and UI claims match actual assurance.
- No merge without human approval and Merger gate revalidation.

## 7. Audit limitations and risk communication

This specification is derived from a repository-focused review, not a formal security assessment. It does not establish runtime behavior across platforms. Implementation must report what was tested, on which platform, with which backend, and what remains unverified. Worktree and application-level controls must not be presented as kernel-enforced isolation.
